# Rosters

Assign signed-up players to squads and roles, manage reserves, then publish the roster to Discord.

Connected websites may read published squads, reserves and native attendance
through the separate `roster-summaries` grant. Editing remains in Logi/Discord.
Drafts, custom guest names, notes and absence reasons are excluded. Unpublishing
removes the shared projection. An acknowledgement or attendance confirmation
does not prove that a player completed a game; websites must preserve that
distinction and apply their own explicit profile publication consent.

## Shared rosters with invited clans

A shared match has one squad roster. In an empty slot's existing player search,
the host can search for and select an accepted clan to allocate that place.
It stays empty until the host or an invited manager selects a player. The clan
label remains visible after a player is selected.

Invited managers can see drafts as well as published rosters. They can fill,
clear or replace players only in their clan's unlocked places. The host can
change every place and can lock an allocated slot immediately; a locked place
is editable only by the host. Only the host can change the layout, allocation,
role details, locks or publication. Reallocating a filled place returns its
player to reserves after confirmation.

Everyone sees the full squad roster. Invited clans see only their own reserves
and not-attending lists; host managers see everyone. Players cannot occupy two
places in the same shared match. If another manager saves first, Logi asks you
to reload before saving so their changes are preserved.

Publishing automatically publishes the roster for all participating clans and
posts it through each clan's existing Discord workflow. Each clan uses its own
channels and message settings. A missing channel or a failed Discord post does
not block the other clans: fix that clan's local settings and its worker retries.

## Build a roster (manager)

<Steps>

### Start from the event context

**Create roster** in a match's Roster tab preselects that match. You can also
start from the workspace roster list and choose a match. If no squad preset
exists, the setup card explains the requirement and links to **Create a squad
preset** for the selected game.

Create a roster from the workspace Roster page and associate it with the appropriate event. Check the event’s sign-ups and attendance information first.

### Choose a layout or template

Add squads and slots manually, or use a squad preset when the standard structure fits. Changing a template later can move or remove layout details, so review the confirmation.

### Place people thoughtfully

Drag a person into a slot, add them to reserves, or mark them not attending. A person can only hold one active place in the roster structure at a time.

### Save as draft, then publish

Publication in Logi and Discord delivery are separate. Publishing without a
Discord destination is allowed: the dialog and confirmation explain that the
roster was saved in Logi and Discord delivery is unavailable, and point to
channel settings. Configure a destination and publish again when ready.

Save while planning. Publish only when you are ready for people to rely on the assignments. **Publish roster** opens the publish dialog, which shows exactly what the bot posts; see [publish to Discord](#publish-to-discord).

Saving requires a current Logi login and current workspace management access.
If either changes while the board is open, sign in again or ask a workspace
administrator before retrying. A roster remains attached to its original event;
templates must belong to the same workspace and game. These checks also apply
to full-access integration writes. Publishing through either writer records the
publication time; the dashboard's Discord publish choices remain in its dialog.

</Steps>

There is one persisted roster per event. Saving a roster reconciles it against
the event: newly tracked attendees become reserves if they are not already in a
squad, while tracked non-attendees go to **not attending**. People who are no
longer tracked are removed. Existing squad placements are preserved during a
normal roster save. A membership or sign-up change refreshes an open match
roster when it has no local edits. Live updates retain an unsaved draft instead
of discarding the manager's changes; review the saved roster after those changes.

Rosters use the same game scope as their event, and a squad preset can only be
applied when it belongs to that game. Legacy records without a game are treated
as Hell Let Loose. Automatic member lists use only memberships for that event's
game; belonging to HLL alone does not add someone to a Wardogs roster. Explicit
event sign-ups and manually placed guests keep their existing behavior.

When starting a new roster, Logi tracks people who had an assignment on or
before the earlier of the current time and the event's registration end, as well
as anyone already in its participant or sign-up lists. An assignment created
after registration closed is therefore not automatically added to that roster's
starting pool. The initial reserve and not-attending lists are sorted by the
workspace score, then name; that order is a starting point, not an automatic
team-selection decision.

## The roster board

Hover or keyboard-focus a player's signup group icon to see their chosen groups
in preference order. These are the choices for this match, separate from their
main and secondary clan groups.

**Auto-fill** optimizes the available players and empty slots together. It fills
as many eligible selected-group slots as possible, then maximizes first choices,
second choices, and subsequent choices in that order. Score breaks preference
ties, followed by K/D; higher-scoring players have priority for better choices.
Existing placements and named guest slots stay in place, and shared-clan slot
allocations still apply. When there are more available players than empty slots,
players whose selected groups have no space stay in reserves. When there are
no surplus players, remaining slots can use random fallback placements outside
the selected groups. Declined players are never used. Review the result and save
or publish it as usual.

The roster opens on the match page under **Roster**, and on its own roster page.
Managers switch the board between three modes at the top: **Overview**,
**Squad editor** (squads and slots) and **Roster editor** (who plays where).
Next to them are the squad preset, **Confirm from meeting VC** with the name of
the meeting voice channel (for example "· Sraz 1") and, in the roster editor,
**Auto-fill**. On phones the preset, the voice-channel confirmation, auto-fill
and deleting or unpublishing sit behind the **⋯** button next to the modes.

Open a roster by clicking its name or anywhere in its table row. The name is
also a normal link for keyboard navigation and opening another tab.

Managers can work directly from **Overview**. The reserves stay in a right-hand
column on wide screens while you scroll through the squads; on smaller screens
they appear above the squads. Each people list takes half of the available sidebar height and has its own scroll area, so scrolling either list does not move the sidebar.
Drag a reserve onto a specific slot, or onto the squad header to fill its first
empty slot. A full squad keeps its players and reports that it has no empty
slots. The assignment button next to a reserve also lets keyboard and phone
users choose a free squad slot.

Drag a squad by its grip onto another squad to place it before that squad and
move it into the same section. Drop onto a section header to append it to that
section. Drag a section by its header grip to move all its squads together;
the up/down buttons offer the same ordering without dragging. Changes remain
local until **Save** or **Publish**. Saved order is also used by the public
roster and Discord's roster text and image; it does not reorder the workspace's
group catalogue.

Right-click a squad, or use its **⋯** button, to edit that squad's name,
section, colour and role slots, edit its players, add a slot, move it up/down,
or remove it. **Finish editing** returns that card to the board's selected
mode. The **+ Add squad** button beside each section creates a unit directly
there. Removing a squad returns its assigned people to reserves.

The existing authenticated `PATCH /api/v1/clan/rosters/{id}` supports the same
layout and assignment changes through its complete roster payload: change
`squads[].group`, provide the saved `squads[].order`, and update the players and
reserve IDs together. A section takes the order of its first squad. API writes
retain their existing clan scope, write grant and idempotency requirements.

- **Unsaved changes: N** counts the edits since the last save: each changed
  slot or squad, and each player moved in or out of the reserves or the
  not-attending list. Save keeps the roster a draft; **Publish roster** asks
  first. Deleting a draft is the bin icon and also asks first.
- The line under the toolbar explains the status icons next to each name: a
  double tick for confirmed by a manager, a tick for confirmed by the player,
  and a clock for not confirmed yet. Managers change the status by clicking the
  icon; in the roster editor the same menu moves the player to the reserves or
  to not attending.
- Each player shows their Discord avatar, group icons, score and K/D, and on
  the right their group. In the roster editor the ⓧ button takes a player out
  of the slot and back to the reserves.
- The reserves and not-attending lists show how many people they hold. Under
  the reserves, **No response: N members** counts members of the match's game
  who have not answered the sign-up; **Remind** sends them the sign-up
  reminder by Discord DM while sign-ups are open. A reminder to the same
  people of a match can be sent once every 30 minutes.
- In the roster editor, drag a player from the reserves into a slot; the free
  slot under the pointer says **Drop here: name**. Or tap a free slot (**Pick
  player**) and choose from the list. Tapping works on phones, where dragging
  does not.
- On phones each squad folds to its header; tap it to open or close it. The
  first squad starts open. **Publish roster** (and **Save** while there are
  unsaved changes) stays at the bottom of the screen.

## Attendance and late changes

Each assigned player and reserve has one of three attendance states:

| State        | Meaning                                                               | How it is set                               |
| ------------ | --------------------------------------------------------------------- | ------------------------------------------- |
| Pending      | No response recorded                                                  | Default, or a manager resets it             |
| Acknowledged | The player used Logi's Discord attendance button, or a manager set it | This is not proof of physical attendance    |
| Confirmed    | Manager-recorded attendance                                           | Used as present attendance in event scoring |

The Discord acknowledgement button works only while the event is **starting**,
the roster is published, and the person is assigned to a squad or reserve. It
cannot add someone to the roster. Managers can update attendance status
directly for a rostered player or reserve.

Managers can also use **Confirm from meeting VC** in the roster's view and
roster editor modes, or **Load from voice channel** under **Sign-ups and
attendance** on the match page. It checks only the
people already assigned to a squad or reserve and marks those currently in the
configured meeting voice/stage channel as confirmed. It does not inspect other
voice channels, move people, add anyone to the roster, or prove that a person
stayed for the event. The action asks the running bot to read each assigned player’s and reserve’s
current voice state directly from Discord’s API, bypassing cached channel
membership. Only those currently in the configured meeting channel are confirmed.
It does not scan the server’s members or store voice states or join/leave logs.
A disconnected player is skipped; permission, network or rate-limit failures
fail the request rather than reporting that nobody is present. The request may
take up to 45 seconds, and an expired request cannot apply a delayed result. The action needs a configured meeting channel and a running
bot with access to read that channel; it is available to managers even if the
roster is not published.

A published roster is visible to non-managers; a draft is not.

## Publish to Discord

**Publish roster** (and **Publish again** for a roster that is already
published) opens one dialog. On the left you choose; on the right a preview
shows the message as it will look in the roster channel.

- **What goes to Discord:** **Photo and text roster** (the default) posts the
  roster image with every squad written out under it, so it can be searched
  and read on a phone. **Photo only** posts just the image, like the old bot.
  The choice is made for each publish; the default comes from **Messages and
  panels → Roster**.
- **Channel:** the event-information channel from **Channels and language**,
  shown read-only. Without a separate channel the match announcement carries
  the roster image instead.
- **Mention event attendees:** on the first publish the message mentions the
  event's temporary attendee role once, rather than every rostered person.
  Discord never pings an edited message, and later publishes do not ping the
  event again. It is off by default when publishing again, because the change
  DMs already reach the people concerned.
- **Counters:** players in the roster, reserves and not attending.

Publishing again edits the same Discord message; no new one is posted. The
dialog's subtitle says when the shown version was published ("published today
at 18:40", "yesterday at …" or the date, in the clan's time zone). It lists the
**changes since the last version** (who is new, who left or went to the
reserves, who moved squad or changed role) and offers:

- **Tell players about changes by DM:** only players whose place changed get a
  DM in the clan language with their new squad and role.
- **Post the change summary to the channel:** a short message under the
  roster. There is one summary per match; each later publish edits it and adds
  the new changes.

Both default to the choice in **Messages and panels → Roster**. Logi keeps
every published version on the server and compares the saved roster with the
version the last publish replaced, so the DMs and the summary always describe
what was actually published, even when another manager published from another
tab in the meantime. The bot sends the DMs and the summary a few seconds after
the save. If some players have
closed DMs, Logi says so after publishing ("The DM did not reach 2 players:
Mrak, Ježek."); the roster is saved either way.

The DMs, the summary and these per-publish choices are dashboard actions. The
clan API (`/api/v1`) publishes a roster with the clan's defaults and without
mentions, DMs or a summary; the defaults themselves are the `matchMessages`
settings slice.

### The roster message

The message title is `Roster · Name · Category · day date · time`, followed by
the map, the meeting time and channel and the filled slots ("18 of 22 places").
With the text roster, squads are grouped under the clan's root groups, one line
per squad with short role names ("F1 · SL Rex_CZ · Medic Medvěd · MG Bizon ·
Rifleman —", where "—" is an open slot), then the reserves and the players not
attending. A roster too long for Discord's 4000-character limit falls back to the
image with **Show full roster**. The footer says when it was published.

The roster image is uploaded to Discord. If image generation temporarily fails
during an update, the existing card stays visible while the bot retries.
Image generation reads the current published roster. Bundled role icons are
loaded directly, and unavailable Discord avatars use a fallback so they do not
block the update. The public roster image is refreshed when it is requested.
Its player rows also show attendance directly: a clock for a player arriving
late and a red X with a red row for a player who cannot attend, including reserves.
The dashboard also highlights these rows in red and keeps the reason available
on the X. In the image, manager-confirmed players have a green row and a green
check mark. Reserves use the same image styling: green after acknowledgement,
and a green check after manager confirmation or confirmation from the meeting
voice channel. On the dashboard, reserves show the same pending, acknowledged
and manager-confirmed status icons as assigned players. An absence notice takes priority over confirmation colouring.

Buttons:

- **Acknowledge** (green), **Running late** and **Can't make it**: every
  rostered player can answer directly from the published roster, even before
  the first attendance reminder is due. Each uses the same confirmation or
  notice flow as the reminder DM, and an early answer means no reminder DM is
  sent.
- **My assignment** (private): your squad, role, squad leader, the leader's
  note, the meeting, and the server with its password. From the meeting start
  it offers **Confirm attendance**; until the game starts **Running late**.
  The attendance reminder DM, sent the day before, can also confirm.
  Reserves see their reserve card; people not on the roster are told so.
- **Show roster** (private): one squad at a time with every role, player and
  whether they confirmed, are pending, are coming late, or cannot attend (an
  X); a menu switches to another squad or the reserves.
- **Open roster:** the public roster page.

### Match forum

When the match has a forum, the bot keeps a **Match information** post (the
announcement's category chip and sides row with the team code chips and
faction emblems, start, map, meeting channel, the server name without its
password, notes and named stratmap links, **My assignment**), one post per
topic of the topic preset, and a pinned **Debrief** post. Once the result is
confirmed, Debrief shows it with **View match**. Discord archives quiet forum
posts; the bot finds its posts again by their stored IDs, archived ones
included, and reopens them to edit them, so a result confirmed days later
updates the same Debrief instead of posting a second one. If **Messages and panels** turns on attendance
notices, a running-late or can't-make-it notice is posted in the match
information thread with the player's name and arrival time; the reason stays in
Logi for the organisers.

### Late signups

Matches allow late signups by default until the meeting starts. A late player
must provide a reason and initially joins reserves. Managers can disable this
in the match settings. A small primary-colour clock marker identifies late
signups; hover or focus it for the reason. The roster image includes a small
clock too, even after the player is assigned to a squad. This is separate from
the attendance action for reporting a late arrival.

Before the game starts, players can change a declined roster confirmation back to
**Confirm attendance** (?). This clears their cannot-attend notice and restores
acknowledgement of their current slot or reserve place. Late-arrival notices remain
until changed separately. If a manager has replaced the player, confirming does
not reclaim their former slot.


### Allocate slots to participating clans

The host can allocate slots while creating a roster or editing an existing one.
The other clan must first accept its match invitation. In assignment mode, click
an open slot and use **Search players or clans**. Choose the clan under
**Allocate to clan** to reserve that role for it, then save the roster. Repeat
for the other slots you want that clan to fill. Choosing a clan leaves the player
empty; the invited clan can fill its unlocked slots. The host can also choose a
specific player directly.

Allocated slots show the clan name and logo. Player choices and filled slots
show small clan logos in shared matches; hovering over a logo identifies the
clan, and missing icons use initials. The host can lock an allocated slot to
retain exclusive editing rights or unlock it to let the invited clan manage it.
The host uses a single lock/unlock icon button, which also shows the current
lock state. Selecting a clan closes the slot picker immediately.
Only the host can publish or unpublish a shared roster. Invited clans see the
host's current publication status and can save their allowed slot edits, without
publish or unpublish controls. Unsaved slot edits do not freeze that status.
In published roster images, a filled slot allocated to another clan shows that
clan's logo instead of the player's avatar. The same slot shows the player's
normal avatar in their own clan's image.
Players already assigned elsewhere remain readable in both light and dark mode.

### Interrupted bot delivery

The updated bot remembers delivery progress for manual reminders, roster-change
notifications, signup reminders and attendance reminders. After a restart it skips
confirmed sends and continues recipients it has not attempted, while rechecking
current eligibility. Confirmed sends still count in the final delivery result.

If Discord may have accepted a message but its confirmation was lost, the bot
keeps that outcome uncertain and does not automatically resend it. This does not
mean the recipient has closed DMs. Check Discord before explicitly sending another
reminder or republishing the roster. Interrupted requests from an older bot without
delivery receipts still require that manual check.

### Sort player suggestions

In the roster overview's player editor and the roster editor, open a slot and
choose **Best role fit**, **Score**, or **K/D** above the search box. Best role fit
uses signup preference and group membership, followed by score and K/D. Score and
K/D sort by the selected metric. Players already assigned elsewhere and players
not attending remain below available attendees. Sorting changes suggestions only;
it does not move players or change automatic roster filling.
