# Clan settings

Clan settings belong to the active workspace. Only managers should change them, and changes can affect how the dashboard, Discord coordination, events, and membership features behave.

## How settings are organised

**Settings** in the sidebar opens an overview. A search field at the top
filters the pages by name and description (for example _channel_, _role_ or
_API key_). While a required step is unfinished, **Workspace setup** shows six
steps with how many are done: the bot on Discord, the games, the clan profile
(a name and a logo; the description is optional), the channels, roles and
access, and, optionally, a game server that collects data. The first unfinished
step is highlighted and **Fix** opens the page that holds it; **Set up** next to
a later step and **Continue setup** open the [setup guide](#setup-guide) at
that step or at the first unfinished one. Below it every settings page is a tile with a
short description and its state, for example **Done**, **1 channel missing**,
**Not set**, **On**/**Off**, the number of games, templates or collecting
servers. A state that cannot be read is left out rather than guessed.

Each tile opens its own page. On a computer the settings menu is on the left,
with a warning sign next to pages that miss a required setting, and the
breadcrumb above shows where you are. On a phone **Settings** at the top leads
back and **Sections** opens the menu; the save bar sits at the bottom of the
screen. Every page saves only its own settings, so saving one page never resets
another.

| Group                    | Page                     | What it contains                                                                                                                           |
| ------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Clan                     | Clan profile             | Name, logo and description, and the Discord invite behind **Join on Discord** on the public clan page                                      |
| Clan                     | Games                    | The games the clan plays                                                                                                                   |
| Clan                     | Event categories         | Labels and colours of matches and trainings, such as Friendly or League                                                                    |
| Matches                  | Match templates          | What a new match or training starts with: times, sign-ups and Discord options                                                              |
| Matches                  | Squad and topic presets  | Links to the squad presets and topic presets, with how many each has                                                                       |
| Discord                  | Channels and language    | Time zone, bot language, announcement, event info, forum and voice rooms                                                                   |
| Discord                  | Messages and panels      | The look of every bot message, what the bot sends and where, the switches of optional messages, the panels and the bot errors channel      |
| Discord                  | Discord panels           | Panels the bot keeps up to date and the panel editor; see [Public Discord panels](/configuration/public-panels)                            |
| Discord                  | Panel graphics           | Default panel style, server banners, map images and the fixed signs; see [Panel graphics](/configuration/panel-graphics)                   |
| Discord                  | Roles and access         | Clan role, dashboard admin role and the dashboard-access resync                                                                            |
| Discord                  | Commands                 | Who may use each slash command, where and how it replies; `/stats` games, sharing channel and old stats servers                            |
| Discord                  | Membership               | Membership applications, categories, roles and roster scores                                                                               |
| Discord                  | Tickets                  | The ticket panel, categories, support roles and questions                                                                                  |

| Website and integrations | Webhooks                 | Signed webhook subscriptions                                                                                                               |

| Maintenance              | Helper data              | Reference data used when importing and matching players                                                                                    |

The former **System**, **Membership settings** and **Ticket settings** addresses
still work and open the matching settings page. The former **Sign-in** page
(`/settings/login`) now opens **Clan website and sign-in**.

Destructive actions on these pages ask for confirmation first and say what
stops working: deleting a webhook, revoking an API key, removing a single
sign-on application, creating a new calendar link and removing a game server or
its key. Empty lists show what is missing and the next step.

Every configuration screen shows its scope above the editor. One game icon means
the change applies only to that selected game; a row of active game icons means
the change is clan-wide. Confirm that scope before saving settings, ticket
panels, membership workflows, or maintenance tools.

**Channels and language** and **Commands** always show the clan-wide
settings, whichever game is selected. On **Channels and language** the fields
are grouped into **Language and time**, **Text channels** and **Voice
channels**; a lock marks a value that is always clan-wide, and a missing
announcements channel is called out at the top. When one game needs a different
announcement, event info, forum, squad voice or meeting room, or its own stats
servers, add an exception for that game under the setting with **Different
channel for a game** (or **Different for a game** in the old stats server
connections on **Commands**). A game without an exception uses the clan-wide value; removing the
exception, or leaving it empty, returns the game to it when you save.
Exceptions are offered when the clan plays more than one game. An exception
stored earlier stays visible, so it can be removed, even after the clan is down
to one game. Exceptions of a game that is switched off are kept but not shown.

## Setup guide

The setup guide walks a new clan through the six setup steps on one full-screen
page (`/dashboard/servers/<clan>/settings/setup`), outside the usual menu. Like
every settings page it is open only to clan admins. The header shows
**Workspace setup** with the clan's name and **Exit the guide**, which returns
to the settings overview; the bar below fills with the finished steps.

On the left the steps are listed with **Required** or **Optional**. A finished
step shows a check, the open step is highlighted, and any step, finished or
not, can be opened again by clicking it. On a phone the list folds into one row
with the open step and how many are done; tap it to see all steps. The card on
the right says **Step N of 6** and holds the step's fields:

| Step                | What you do                                                                                                                                   | Finished when                       |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 1. Bot on Discord   | See whether the bot is on the clan's server and can read its channels and roles; **Invite the bot** if not, then **Check again**              | The bot is on the server            |
| 2. Games            | Choose the games the clan plays; at least one                                                                                                 | A game is chosen                    |
| 3. Clan profile     | Clan name, logo (PNG or JPG) and an optional description                                                                                      | The clan has a name and a logo      |
| 4. Channels         | Announcements, event information and, optionally, bot errors; per-game exceptions stay on **Channels and language**                           | The announcements channel is chosen |
| 5. Roles and access | The clan role and the Logi admin role                                                                                                         | The clan role is chosen             |
| 6. Game servers     | Optional: **Connect a server** opens the same form as **Game servers**; the connection is tested before it is saved, and the key is encrypted | A connected server collects data    |

**Continue** saves the step and opens the next one; nothing is saved when the
step was not changed. **Skip** moves on without saving, and **Back** returns to
the previous step without saving. On the last step the button reads
**Finish** and leads to **Done. Logi is ready.**, with **Open Settings** and
**Go through again**. On a phone **Back**, **Skip** and **Continue** sit in a
bar at the bottom of the screen.

The guide saves exactly what the matching settings pages save and decides
which steps are finished by the same rule as **Workspace setup** on the
settings overview, so both always agree. Opening the guide without a step
starts at the first unfinished one; when every step is finished it opens on
the closing screen.

## Change settings carefully

<Steps>

### Confirm the workspace

Check the server name in the sidebar before changing anything. Settings apply to that server, not to every community you can access.

### Change one concern at a time

Review the relevant section, make the smallest intended change, and save it.

### Verify in the affected feature

For example, after a scheduling or Discord-related change, inspect an event or the related Discord configuration rather than assuming the setting took effect as expected.

</Steps>

## Integrations, API keys, and Discord metadata

### Preview a Wardogs League match

For scheduled discovery, manual tracking and the WD League panels in Discord, see [Wardogs League](/wiki/configuration/league-tracking). The standalone preview below remains available without registering a match.

Open **Settings → Wardogs League**; the **Wardogs League match** preview is below the tracking form.
Paste a public `https://wardogsleague.net/matches/{id}` link and choose **Load match**.
The preview shows the schedule in Europe/Prague, teams with their factions,
map/zone/lighting, public hosting, moderator, map voting, rules and preparation steps.
Team member counts describe the team profile; they are not the match roster.
Reading the link does not create an event or confirm results.

No League account or Team API key is needed. Logi refreshes on request, at most
once every five minutes per match. If a refresh fails, the last saved match
remains visible with a stale warning, collection time and next allowed refresh.
Missing fields remain unknown. Only the Scheduled page format has live validation;
results, placements and no-show interpretation are not supported yet.

Website backends can request the same preview with an API key explicitly granting
**Public Wardogs League matches** (`league-matches`) and **Wardogs**:
`GET /api/v1/clan/league-matches?game=wardogs&url=<URL-encoded-public-match-link>`.
Poll every 5–10 minutes and honor `nextRefreshAt` and `Retry-After`. Inspect `stale`
and `fetchedAt` before presenting cached data as current. Legacy full-access keys
do not grant this new read. Server passwords and join IDs are never returned.

## Games

The **Games** section controls which games are active for this workspace:
**Hell Let Loose**, **Hell Let Loose: Vietnam**, and **Wardogs**. A workspace
may enable any combination, including none while it is being configured.

Game-specific Discord channels and stats servers are exceptions on the
**Channels and language** and **Commands** pages (see above). Other
game-specific settings, such as public panel wording and membership-application
categories, are edited after choosing that game in the dashboard. Shared Discord
identity, workspace-level settings, and platform links are not duplicated per
game.

When no games are active, Logi prevents creation of game-owned records and
links to this settings section. When exactly one is active, creation pages
select it automatically. With multiple games active, starting a game-owned
creation flow from **All games** first asks the manager to choose a game.

Integrations have their own manager-only settings pages: **Clan website and sign-in** (website API keys, the sign-in page, single sign-on applications, Discord membership integrations and website event commands), **Google Calendar** and **Webhooks**; imports and helper data are under **Maintenance**. Treat keys, webhook signing secrets, and secret configuration as sensitive: never paste them into articles, roster notes, public screenshots, or support messages.

Each website API key belongs to the currently selected workspace. Its permissions
determine which data it can read or change. Give it a recognisable name of at most 80
characters. The full value is displayed once, at creation time; afterward the
dashboard shows its prefix, creation date, granted resources/games, and whether
it has been revoked. Revoking a key takes effect for future requests and cannot be undone:
create and deploy a replacement key before revoking one used by a live site.

#### Read-only integration keys

In **Settings → Clan website and sign-in → API key for the website**, press **New key** (the form is already open while the clan has no key). It starts with **Read-only** access and
the **Matches** area selected. Access is chosen by area instead of one box per
resource: **Matches** (events, matches, their summaries and strat maps),
**Rosters**, **Results** (confirmed results, player statistics and game
history), **Members**, **Game servers** (live server data, Warcon, HLL and
connection health) and **League and teams**. Choose the required
games explicitly; an empty area or game selection cannot create a restricted
key. Each key is listed as one line, for example _read only · matches, members ·
every game_; keys created before areas existed show an area they cover only in
part as _(part)_. Review the selection, enter a name and press **Create read-only key**.
Copy the revealed key before hiding it or leaving the workspace. It is never
available from the existing-key list.

Choose **Full access (legacy)** only when an integration needs write access.
That mode can read and modify all clan data across all games. Existing keys
keep their permissions; restricted and legacy keys are clearly distinguished
in the list. To change a policy, create a replacement key, switch the integration,
and then revoke its old key. The interface is localized in English, Czech and German.

Administrators can also issue a restricted key through the existing authenticated
`POST /api/servers/{serverId}/api-keys` endpoint by including a `readAccess`
object alongside `name`:

```json
{
    "name": "Website summary reader",
    "readAccess": {
        "resources": ["event-summaries", "match-summaries"],
        "gameIds": ["hell_let_loose", "wardogs"]
    }
}
```

Both arrays must be nonempty and contain no duplicates. Resources can be
`server-snapshots`, `integration-health`, `event-summaries`, `match-summaries`, `events`, `groups`, `rosters`,
`assignments`, `stratmaps` or `matches`; game IDs
can be `hell_let_loose`, `hell_let_loose_vietnam` or `wardogs`. Each collection
request must select explicit permitted games. Missing `game`, `game=all`,
ungranted resources and all writes return `403 insufficient_scope`. Detail
reads check the stored tenant and game. Revocation is checked on every backend
operation, and restricted reads are not cached by HTTP clients.

Requests without `readAccess` still create full-access legacy keys, including
the form's explicit full-access option. Existing keys are not automatically restricted.
Use a newly issued restricted key for a read-only website and revoke the old
credential after switching it. The management list endpoint includes the stored
policy. A bearer key cannot create or broaden keys; that requires a dashboard
administrator session.

Restricted keys do not grant metadata, settings, raw users, calendar items,
presets or performance history in this first release. Read-only records still
require publication review: never publish raw API responses. The
[versioned website handoff](https://github.com/Ninjonik/logi/blob/main/docs/integrations/website/v0.5/README.md)
describes field allowlists, safe synchronization, fixtures and rollout order.
Deploy the compatible backend before using these new policies; an older backend
does not enforce them.

For website event and result listings, use `GET /api/v1/clan/event-summaries`
and `GET /api/v1/clan/match-summaries`, with an explicit game. These return
only identity, title, schedule/status or a minimized imported result. They
exclude passwords, notes, signup/player identities, source URLs and raw
telemetry. Each summary resource requires its own grant; it does not grant
access to the raw `events` or `matches` resource, or vice versa.

Both summary detail routes use the Logi event ID. Match summaries exclude
training events. No stored event result means `resultState: "unknown"` and
`result: null`; an imported event result is `provisional`, including for
concluded events. The website still approves publication and translations.
These routes do not provide human result confirmation or public-member consent.

For Logi's global team catalogue, issue a restricted key that grants `teams` for
each game the website may read, then use
`GET /api/v1/clan/teams?game=hell_let_loose` (or `game=wardogs`) and
`GET /api/v1/clan/teams/{id}?game=...`. Exactly one game is required; Hell Let
Loose: Vietnam has no team catalogue. The reads return only active teams with
their ID, game, name, short code, public logo URL, revision and update time;
archived and merged teams are omitted. Legacy full-access keys never grant this
read. Event and match summaries carry the teams captured for each native match,
which keep their names and logos after a team is renamed, archived or merged.
Logi's global administrators create, edit, archive, merge and restore catalogue
teams and upload their logos; workspaces request additions and changes. None of
these has an API-key equivalent. The
[team directory handoff](https://github.com/Ninjonik/logi/blob/main/docs/integrations/website/v0.15/README.md)
describes the change feed, fixtures and match assignment commands.

Website integrations use the versioned API at `/api/v1`. Clan API requests
use `Authorization: Bearer <API key>`. Game-owned clan data uses **Hell Let
Loose** for legacy keys when no `game` query parameter is supplied, including legacy records;
use `game=hell_let_loose_vietnam`, `game=wardogs`, or `game=all` to select
another scope. List requests are cursor-paginated, default to 25 records, and
are capped at 100 records. Every game-owned returned record has an explicit `gameId`, so a
website can safely cache and combine data from more than one game. The live,
machine-readable contract is available at `/api/v1/openapi.json` and the
interactive reference at `/api/v1/docs`.

Authenticated clan API requests may make **60 requests per second per API
key**; public endpoints are limited per client IP. This does not apply to
dashboard routes. A limited request returns `429` with `Retry-After` and
`RateLimit-*` headers. Clients should back off and retry only after that delay.

Start with the API key in an `Authorization` header; never put it in a URL or
client-side bundle. The key is tenant-scoped: it can access only the workspace
that created it and only operations permitted by its policy. A record ID from
another workspace is not usable. Writes below require a legacy full-access key.

```bash
curl -H "Authorization: Bearer YOUR_API_KEY" \
  "https://YOUR_LOGI_HOST/api/v1/clan/events?game=wardogs&limit=25&updatedSince=2026-01-01T00:00:00Z"
```

List responses contain `data` and `page.nextCursor`. Treat that cursor as an
opaque value: send it only to the same resource with the same `game` and
`sort=createdAt` selection. To retrieve one known record, use
`GET /api/v1/clan/events/{id}`. `updatedSince` accepts an ISO timestamp and is
useful for incremental synchronization; it includes records updated at or
after that time.

For a write, generate one new visible idempotency key and retain it until the
request is resolved. If a network timeout leaves the result unknown, repeat
the exact method, URL, body, and key to receive the original result. Reusing a
key for changed content returns `409 idempotency_conflict`, so changed work
needs a new key. Invalid inputs return `400` with
`{ "error": { "code": "validation_error", "message": "..." } }`.

```bash
curl -X POST "https://YOUR_LOGI_HOST/api/v1/clan/events" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: event-create-42" \
  --data '{"kind":"training","name":"Training","registrationEnd":"2030-01-01T18:00:00Z","meetingStart":"2030-01-01T19:00:00Z","pingClan":false}'
```

Roster and member synchronization can use `updatedSince` on their respective
list endpoints. Member pages contain one record per workspace member even when
that person has assignments in multiple games.

The API currently supports article writes, group create/update/delete, event
create/update, stratmap create/update, topic-preset create/update, squad-preset
create/update, roster update/delete, assignment create/update/delete, the named
event conclude action, and event signup changes. Event
deletion is intentionally unsupported because its roster, match, Discord, and
scheduled-job dependencies have no safe deletion lifecycle. Every write requires an `Idempotency-Key`; repeating the
same request with the same key replays its original result for 24 hours. Group
deletion also clears that group's references from workspace assignments. An
event signup request uses
`POST /api/v1/clan/events/{eventId}/signup` with a JSON `userId` and `group`
(a group string or `null`). It applies the same signup eligibility and
registration-window rules as the dashboard.

Event creation and updates use `POST /api/v1/clan/events` and
`PATCH /api/v1/clan/events/{eventId}` with the same complete event form used by
the dashboard. Referenced signup groups, stratmaps, and topic presets must
belong to the authenticated workspace. Successful creates emit `event.created`;
updates and `POST /api/v1/clan/events/{eventId}/actions/conclude` emit
`event.updated`.

Match team selections (`matchTeams`) are read-only on these two endpoints,
because an API key alone is not a writing actor. A sent selection is ignored
and the saved one is kept; a game change that the saved teams no longer fit
returns `validation_error`, and changing an unconcluded match into a training
clears its teams. A connected website selects teams through the signed-in
[website event commands](/wiki/operations/events#connected-clan-websites).
Complete event records from `GET /api/v1/clan/events` keep each saved team's
full snapshot, including an internal logo reference that is not a URL; show
team names and logos from the `matchTeams` of the event or match summaries,
which carry only the public `logoUrl`.

Stratmaps and presets use `POST /api/v1/clan/stratmaps`,
`POST /api/v1/clan/topic-presets`, and `POST /api/v1/clan/squad-presets`, with
the corresponding `PATCH /{id}` paths for complete dashboard-equivalent
updates. These resources are intentionally non-deletable through the API:
existing event, roster, and Discord-forum references do not have a safe cleanup
lifecycle for a bearer key, which cannot confirm the loss. A manager can delete
a stratmap in the dashboard after a confirmation that names the events losing
it; Logi then removes it from those events. A
stratmap's referenced event must belong to the authenticated workspace and use
the same game. Topic preset attachment limits are the same as the dashboard.

Roster updates use `PATCH /api/v1/clan/rosters/{rosterId}` and must include the
complete roster form for that same event. Only unpublished rosters can be
deleted. Assignment changes use `/api/v1/clan/assignments`; they rebuild the
workspace and user membership state and synchronize open matching-game rosters.
An assignment cannot be moved to another user or game through `PATCH`. Logi emits one
`roster.updated` webhook after a roster write, or after an assignment change
that updates at least one open roster.

`PATCH /api/v1/clan/settings` changes only explicitly supplied safe workspace
and Discord fields. It cannot write runtime credentials, player-stat tokens,
ticket or membership workflows, or game overrides; omitted settings remain
unchanged. Feature settings come in named groups: `GET` returns them under
`data.slices`, and `PATCH` changes one group with `{ "<group>": { … } }`, again
only the supplied fields. The OpenAPI reference lists every group and its
fields.

<Callout type="warning">
    Do not rotate, delete, or reveal an API key unless you understand every
    integration using it. A broken key can interrupt an external integration
    immediately.
</Callout>

### Webhooks

Workspace administrators can add an HTTPS webhook endpoint in **Settings → Webhooks** and send a test event.
Logi signs the exact JSON payload using `X-Logi-Signature` as
`sha256=<HMAC_SHA256(timestamp + "." + rawBody)>`; use `X-Logi-Timestamp` to
reject stale requests. The signing secret is revealed only when a subscription
is created or rotated. Current mutation events include article creation, update, and
deletion; event creation and updates; and roster updates caused by API event-signup changes. Failed transient deliveries retry with bounded backoff; permanent
4xx responses do not retry except `408` and `429`. Delivery history records
successful, failed, and retried attempts and keeps finished deliveries for 30
days; deleting or disabling a subscription prevents queued deliveries from
being sent, and deleting it also removes its delivery history.

Each delivery is an HTTP `POST` with `Content-Type: application/json` and
`User-Agent: Logi-Webhooks/1.0`. The body has this exact JSON envelope. The
`id` is a UUID identifying the event; `X-Logi-Delivery` is the persisted
delivery-attempt ID and is intentionally different.

```json
{
    "id": "UUID event ID",
    "type": "event.updated",
    "createdAt": "2026-09-26T10:00:00.000Z",
    "guildId": "your-discord-guild-id",
    "resource": { "type-specific API response data" }
}
```

The request also includes `X-Logi-Event` (the same value as body `type`),
`X-Logi-Delivery`, `X-Logi-Timestamp` (Unix seconds), and
`X-Logi-Signature`. Verify a delivery before parsing or acting on it:
calculate HMAC-SHA256 over the exact `X-Logi-Timestamp`, a dot, and the raw
request body with the signing secret, then compare it to
`X-Logi-Signature` and reject timestamps outside your allowed replay window.
The signature is formatted as `sha256=<hex digest>`. A disabled or deleted
subscription stops pending deliveries from being sent.

### Event types

New webhook subscriptions receive all production event types below. Configure
your endpoint to accept them before enabling the subscription:

| Event type         | Exact trigger                                                                                        | `resource` shape                                                                                                                                                                                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `article.created`  | Successful `POST /api/v1/clan/articles`                                                              | Created [article API object](/api/v1/docs#tag/Clan-API-%E2%80%94-Articles).                                                                                                                                                                                      |
| `article.updated`  | Successful `PATCH /api/v1/clan/articles/{id}`                                                        | Updated [article API object](/api/v1/docs#tag/Clan-API-%E2%80%94-Articles).                                                                                                                                                                                      |
| `article.deleted`  | Successful `DELETE /api/v1/clan/articles/{id}`                                                       | `{ "id": "article-id", "deleted": true }`.                                                                                                                                                                                                                       |
| `event.created`    | Successful `POST /api/v1/clan/events`                                                                | Created [event API object](/api/v1/docs#tag/Clan-API-%E2%80%94-Events).                                                                                                                                                                                          |
| `event.updated`    | Successful `PATCH /api/v1/clan/events/{id}` or `POST /api/v1/clan/events/{id}/actions/conclude`      | Updated [event API object](/api/v1/docs#tag/Clan-API-%E2%80%94-Events).                                                                                                                                                                                          |
| `roster.updated`   | Successful roster update/delete, event signup write, or assignment write that affects an open roster | [Roster API object](/api/v1/docs#tag/Clan-API-%E2%80%94-Rosters) or `{ id, deleted: true }`; signup result from [Events](/api/v1/docs#tag/Clan-API-%E2%80%94-Events); or [assignment API object](/api/v1/docs#tag/Clan-API-%E2%80%94-Assignments), respectively. |
| `settings.updated` | Successful `PATCH /api/v1/clan/settings`                                                             | `{ guild, discordConfig, slices }`, with sensitive Discord data removed; see [Settings](/api/v1/docs#tag/Clan-API-%E2%80%94-Settings).                                                                                                                           |
| `webhook.test`     | A manager presses **Send test**                                                                      | `{ "test": true }`; sent only to that selected webhook, regardless of its subscribed types.                                                                                                                                                                      |

The article, event, roster, and assignment API object schemas are the same as
the successful response `data` for the named `/api/v1` endpoint. Consult the
interactive API reference at `/api/v1/docs` for their complete field-level
schemas. Only successful writes enqueue production webhook events.

## Discord settings: what each field actually enables

Saving a channel or role selection does not prove that the bot can use it. The
bot must still be in this Discord server, be running, and have the channel and
role permissions required for the relevant action.

| Setting                     | Enables                                                                     | If blank, invalid, or inaccessible                                                                                                                          |
| --------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Timezone                    | Dashboard formatting for this workspace and event-entry conversion          | Times fall back to the relevant display default; it does not change existing stored timestamps.                                                             |
| Default language            | Bot panel, event, and interaction wording                                   | Existing content is not translated; the bot uses its configured fallback where needed.                                                                      |
| Announcements channel       | Event announcement messages                                                 | No announcement is created there.                                                                                                                           |
| Event information channel   | Separate match information message                                          | The separate message is not created. It is meaningful only alongside announcements.                                                                         |
| Errors channel              | Bot error reports for managers, set on **Messages and panels**              | Errors remain in the bot's logs rather than reaching a staff Discord channel.                                                                               |
| Calendar channel            | One managed calendar-panel message, set on **Discord panels**               | No Discord calendar panel is maintained. Removing the calendar panel removes its message.                                                                   |
| Forum category              | Match forum-post provisioning                                               | A match cannot get a Logi forum post from the workspace default.                                                                                            |
| Meeting voice/stage channel | Discord scheduled event and meeting-channel attendance tools                | No scheduled event is maintained. A text/category channel is not a substitute.                                                                              |

### Messages and panels, Roles and access, and Commands

**Messages and panels** (in the Discord group, after **Channels and language**)
shows everything the bot sends: where it goes, whether it is sent at all and how
it looks. The bot writes in the clan language with the clan colour. The page is
clan-wide, whichever game is selected.

**Look of all messages** applies to announcements, panels, direct messages and
command replies:

- **Clan colour** is the bar of every message. Without a clan colour messages
  use Logi orange (`#E8A33D`). An event category shows as a label and does not
  change the bar; a panel can have its own colour in the panel editor.
- **Icons in messages** is either **Sparse** or **Emoji on every line**, in
  every message, not only in announcements.
- **Faction signs** shows the signs used in announcements, results, panels and
  `/stats`; **Change signs** opens [Panel graphics](/configuration/panel-graphics).
- **Language** shows the clan language with a link to **Channels and
  language**, where it is changed.
- **Live preview** draws a match announcement and changes with the colour and
  icons as you edit them.

**What the bot sends** lists every message in five groups: **Matches**,
**Private messages** (DMs and replies only one person sees), **Panels**,
**Membership and tickets** and **System**. Each row says where the message goes.
A channel with a lock belongs to another page and links there (for example the
announcements channel on **Channels and language**, the recruitment channel on
**Membership**); a game with its own channel is shown next to the clan-wide one.
**Preview** opens an example of the message with sample data, in the clan
language. Every preview is drawn by the same code the bot uses to post the
message, so it shows exactly what Discord shows; the recruitment and ticket
previews use the clan's own panel title, text, colour and categories once they
are set on **Membership** and **Tickets**.

The absence and late posts never contain the reason; only the leaders see it,

**Panels** lists every panel of **Discord panels**: the live server panels,
**Our servers**, the **Server control** messages of server seeding, the results

calendar and the competition tables, each with its channel. The list reads the
same state as **Discord panels** and refreshes itself: a chip shows **Error**,
**Waiting for the bot**, **Not sent** or **Paused**; a published panel has no
chip. An error row says the cause in one short sentence (for example the
missing permission and the channel); a private-channel server panel that shows
the server password says so; the calendar names its event categories, and a
paused panel says who paused it. A panel's switch pauses or resumes it (**Save**
sends the change, also when nothing else changed); a panel not sent yet is sent

**Bot errors** holds the **Channel for bot errors**. The bot posts there what it

A bar at the bottom counts unsaved changes; **Save** stores the look, the

**Roles and access** has the clan role and the manager role, each with how many

most every six hours; joins, leaves and role changes of single members arrive
in between as they happen.

saved manager role; it is available once a manager role is saved and the page

On these pages a bar at the bottom counts unsaved changes; **Discard** returns

## Game server data

In **Settings → Game servers**, workspace administrators connect their own game
servers with **Connect server** (the form is already open while no server is
connected). For each server enter a name, choose the **server type** (CRCON,
Warcon, RCON or the public Wardog Servers list; the game follows from the type),
the HTTPS address without a path, the server ID at the provider (the
CRCON server number, usually `1`, or the Warcon panel's server UUID) and the API
key. **Test connection** makes one read-only request and checks that the key
works for exactly that server. **Save and start collecting** becomes available
only after a test of exactly the entered values passed; changing a field asks
for a new test. Saving stores the key encrypted and starts collection. The Wardog
Servers directory needs no key; a CRCON key is optional and, without one, Logi
reads only public data. A CRCON key's user needs permission to view connection
information.

A saved key is never shown again and cannot be exported. Each server card
shows its state (**Collecting**, **Paused by an error**, **Not collecting**),
whether a key is stored and when it was changed, the last test and how long
ago it ran, and the **last game**: the map the collector last saw and when. A source **paused by an error** is still switched on: Logi retries it and the card keeps the **Stop collecting** button next to the key actions, so it can be turned off without a working key. A
stopped server says what to do instead, for example to create a new CRCON key
that may read server information and enter it with **Change key**. For a
collecting Warcon server, **Live score** in the **…** menu opens the live
scoreboard. **Keep played games** sets how long history is kept and **Browse
played games** opens the retained history. **Change key** tests
the new key first and replaces the old one only if the test passes, unless you
explicitly save it as unverified, which stops collection until a test passes.
**Test saved key** re-checks the stored key. **Rename**, **Remove key** and
**Remove server** are in the server's **…** menu and the two removals ask for
confirmation first: **Remove key** deletes the key and stops collection (a CRCON
server can then be started again without a key) and **Remove server** stops
collection and deletes the key while keeping collected history. The address and server ID
cannot be edited: connect a new server instead. Names are unique within the
workspace; up to 20 servers can be connected, and connection tests are limited
to 30 per workspace, 6 per server and 30 per administrator every 10 minutes. For
an operator server reachable only through an operator network exception, save a
new key as unverified and then use **Test saved key**.

Servers configured by the Logi operator appear as **Configured by the Logi
operator**. You can test them and replace their key, but not rename or remove
them. A server registered before encrypted keys that named an environment
variable shows **Old key reference** and does not collect until you enter its key
again or the operator migrates it. If Logi reports that the stored key cannot be
used because the encryption key is unavailable, contact the Logi operator. If
encrypted key storage is not activated on the deployment, keys can be tested but
not saved.

HLL CRCON supports current server data and historical match collection. Wardogs
RCON supports current server data after checking its available functions. An
optional Wardog Servers directory source provides public status with attribution.
The **Wardogs Warcon** provider reads an existing Warcon panel, including live
players and completed matches. It is distinct from a direct Wardogs RCON source.
Select one source for a server; Logi does not silently replace it with another.

Cards show players, map, last observation, data freshness and any provider error.
The collector checks for due servers every thirty seconds, collecting at most ten
servers per tick with two reads in parallel. Each server keeps its normal polling
interval (usually sixty seconds) or a longer interval required by its provider.
Retry delays and rate limits are respected; a large backlog or a provider failure
can delay the next observation. Older due servers are served first across workspaces.
HLL and Warcon also show the number of collected sessions and last successful history
import. Zero players is a known value; unknown is different. Old counts remain
visible with their timestamp when a source fails. Data becomes stale after three
minutes and unavailable after fifteen; disabling a source makes it unavailable
immediately. A missing directory entry does not prove that the server is offline.

**Disable** (or **Stop collecting**) stops collection and rejects in-flight
results from older runs; so does a key change. If the provider rejects the key,
change it and run **Test saved key** before **Start collecting**. **Refresh** reloads Logi's stored status; it does not contact
the game server. A history-import error is displayed separately from current data.

Website keys need the **Server snapshots** and/or **Integration health** grants
and an explicit game. Read `/api/v1/clan/server-snapshots?game=wardogs` or
`/api/v1/clan/integration-health?game=hell_let_loose`; details use the Logi
connection ID. These are read-only resources. Provider credentials, addresses
and private player identities are excluded. Live scores and imported sessions
remain unconfirmed; they do not create a verified player link or approved match
result. No game-server controls are provided by this screen or these API routes.

Discord server managers can also use `/server-status` with a game to see a private
summary of stored observations and their freshness. A server whose data is no
longer fresh keeps its last known state for a day, marked stale with the
observation time ("Online · stale · 25 minutes ago"); after a day it reads
"No data". The command does not trigger collection; the full connection list
stays in settings.

### Warcon live scoreboard and website reads

An enabled Warcon connection has a **Live Warcon scoreboard** panel. Expand it
to see current players, faction scores, kills/deaths, K/D, cash, ping and the game
join code. It refreshes every 15 seconds while open in a visible tab. Its refresh
button requests a live view, which can reuse a shared ten-second cache.

Player and status timestamps are separate. This live view becomes stale after
45 seconds and unavailable after three minutes; unavailable player rows are
hidden. These thresholds differ from the stored snapshot card above. Missing
values are unknown, while a displayed zero is a measurement. Failed reads show
an error instead of leaving a player table labeled as current.

For the website, create a read-only key with the explicit **Warcon gameplay
data** grant and **Wardogs** selected. Legacy full-access keys do not implicitly
include it. The grant includes game display names and Steam IDs; only publish
those according to your community's policy. Keep the key in your website backend.

Read `/api/v1/clan/warcon-data/{connectionId}?game=wardogs&view=live`. Other views
provide analytics, cash history, match pages/details, leaderboard, seen players,
career, kills, catalogs, rotation and API health/capabilities. See the
[Warcon integration guide](https://github.com/Ninjonik/logi/blob/main/docs/integrations/website/v0.11/README.md)
and [API documentation](/api/v1/docs) for parameters and permissions. Map filters
use IDs from the catalog, which can differ from live display names.

A disabled kill feed remains disabled; Logi does not turn it on. Imported matches
and player observations remain unconfirmed and do not establish account ownership.
The scoreboard and website API provide reads only. Ban lists, staff notes, private
server configuration and administrative actions are outside this integration.

Changing a data source and managing website API keys require a current signed-in
administrator. Logi checks the session and workspace permission again when saving
the change. A pending Warcon read also rechecks access before returning provider
data. After signing out or losing administrator access, refresh the page and sign
in with an authorized account before trying again.

Wardogs League refreshes honor the provider's retry delay, up to 24 hours per
response. Existing saved data remains visible with its age while refresh is
unavailable; a provider error never replaces it with an empty match.

## Imports, performance, and helper data

The **Imports** section is manager-only operational maintenance. Each action uses
the game selected in the dashboard game switcher; when no game is selected, it
defaults to **Hell Let Loose**. The exact
member-import and linking safeguards are documented in
[Members and groups](/wiki/configuration/members). Two other controls are easy
to misunderstand:

- **Refresh performance history** rebuilds the workspace and player trend
  snapshots from recorded, non-training events with imported match statistics.
  The charts retain at most the ten most recent qualifying matches. It does not
  import a scoreboard, create a match result, or change a member's stored
  all-time performance summary.
- **Initialize helper data** first clears helper data, then creates the bundled
  default group hierarchy and one HLL Standard Lineup squad preset. It does not
  restore previously customised groups, topic presets, or squad layouts.
- **Reset helper data** deletes this workspace's groups, squad presets, and
  topic presets. It also clears group selections from assignments, topic-preset
  selections from events, and squad-preset selections from rosters. It leaves
  people, assignments, events, and rosters themselves in place. There is no
  recovery action in the dashboard.

Use reset only when deliberately starting these helper structures over, and
check events and rosters afterward because their preset references will have
been removed.

### Durable website synchronization

Restricted integrations can capture a baseline revision with
`GET /api/v1/clan/changes?start=now` and refetch a current record atomically at
`GET /api/v1/clan/sync-records/{resource}/{id}?game=wardogs`. Both require explicit
underlying read grants and one game. Logi does not retain a replay log of every
mutation: a cursor response is `410 reset_required`, so rebuild the integration's
own baseline when recovery is needed. Keep CMS/publication decisions in the
website's own backend.

The registered projections are event summaries, match summaries and reviewed
result summaries. Server snapshots and integration health are live state with no
invalidations: read them from `/api/v1/clan/server-snapshots` and
`/api/v1/clan/integration-health`. Optional `integration.changed` webhook subscriptions emit
minimal invalidations from dashboard, API, bot, import and collector transactions.
Use the existing administrator-session webhook endpoint to opt into that event
type; existing subscriptions are unchanged. The queue processes bounded batches,
honors Retry-After and recovers expired worker leases. Receivers must deduplicate
and rebuild their own baseline after an outage. See `/api/v1/docs` for the contract.

### Reviewed result access

Select **Reviewed result summaries** explicitly when creating a restricted key;
the existing event/match defaults do not include it. Read
`/api/v1/clan/result-summaries?game=hell_let_loose`, or a detail using its event ID.
The response distinguishes unknown, provisional, confirmed and corrected results,
preserves zero versus unknown scores, and supports multiple factions. It omits
private player/reviewer identities and correction notes. Confirmation and
correction require a signed-in manager in Logi; an integration key cannot do them.
Existing match summaries retain their earlier import-only semantics.

## Dashboard writes behind a reverse proxy

The Logi operator must set `SITE_URL` to the public dashboard URL, such as
`https://logibot.tech`. Dashboard writes check the browser's origin against that
configured URL, even when a proxy forwards requests to an internal HTTP address.
The check still requires the current session and each action's existing workspace
permissions. If pages load but saving event registrations, provider sources,
restricted API keys or integration policies is denied, check both the current
administrator session and this public URL configuration. Do not substitute an
API key or disable the origin check.

## Discord membership integrations

Create a read-only key with the Discord membership resource and selected games in
step 1 of **Clan website and sign-in**. In step 3, **Find out who is a member**,
refresh, pick the allowed Discord roles per game by name, enable the policy and
save. Blank role lists share only presence and
Logi assignment. Policy administration requires your signed-in server administrator
session; API keys cannot change these permissions.

Membership reads return an explicit unknown state when fresh Discord evidence is
unavailable. They never expose all roles or grant website administration. Policy
changes and reconnects invalidate cached authority. Membership feed consumers must
specify one Discord subject and handle a scope reset. `membership.changed`
webhooks are no longer sent; poll the membership feed instead. Existing summary
keys and webhook subscriptions do not gain member access automatically.

## Website event commands

A connected website may create, update or cancel events through its own service
key only when a manager enables a policy for it. Open **Settings → Clan website and sign-in → Create and
edit events** (step 3), choose the registered single sign-on application, and for each live
restricted API key pick the allowed Discord roles per game by name,
tick **Allow event commands with this key** and save. Saving grants event-command
write access for the games that have at least one role; a game without roles stays
read-only, and disabling the policy removes the grant again.

The form only offers restricted keys of the current workspace and applications
registered in it; legacy unrestricted keys never qualify. Members must also hold one
of the listed roles in a fresh Discord observation when the website issues a
command, so a role list is a ceiling, not a guarantee. Policy administration needs
your signed-in server administrator session; API keys cannot change it.

### Choosing Discord channels

All channel fields use the same searchable dropdown. Search by channel name or
Discord channel ID; each result shows both. Fields for one destination close after
you select a channel. Fields that allow multiple channels stay open: select a
channel again to remove it, or choose the empty option to clear the selection.
Only channel types supported by the setting are offered. Saved channels missing
from Discord remain visible by ID with a reminder to check access. If the channel
list is unavailable, paste a channel ID into the search and select it.

### One results channel for every game

In **Channels and language**, set **Event results** to a text or announcement
channel. This is a clan-wide default with no per-game exceptions. It also appears in
guided setup and is linked from Discord messages. The match creation Discord
step lets you select its results channel beside registration and event info;
that selection is saved with the match. It is separate
from registration, event information and the optional game-specific results
panels. The bot posts a scored image for concluded matches after the result has
been confirmed, edits it after corrections, and includes available statistics
links. Leaving the channel empty disables these shared result posts.

The same setting is exposed as the clearable `eventResultsChannelId` field in
`GET/PATCH /api/v1/clan/settings`. See [Matches](/operations/matches) for automatic
match pictures, result images, timezone behavior and image API access.
