# Clan applications

## Applications handled by an external Discord bot

An external bot can run its own application form, thread and moderator decisions
and use `POST /api/v1/clan/users/register` only to create or update the applicant's
Logi account. This endpoint does **not** create a native Logi application, grant
Discord roles, or create or update membership by default (`createMembership=false`).
Existing HLL/Wardogs assignments and statuses remain unchanged.

The integration authenticates the applicant's Discord identity and sends its
clan's `guildId`, the applicant's `discordId` and `name`, and, when needed, a
Steam ID64. Existing accounts are reused; an unclaimed Steam ID is appended
without replacing other linked accounts, the Discord identity, name or avatar.
An existing user can omit `steamId` if Logi already has a linked Steam ID.
New users and users without Steam details must provide one. This is self-declared
account metadata; Steam OpenID verification remains a separate user action.

If another user already has the Steam ID, registration returns HTTP 409 and
changes nothing. It checks numeric IDs, `steam:` IDs, profile URLs and active
verified Steam links. It never transfers a Steam account between users. The
applicant should correct their Steam ID or ask an administrator to resolve the
existing link; automatic unlinking through a clan key is deliberately excluded.

The API requires a full-access clan key and `Idempotency-Key`; `guildId` must
match that key. Retry with the identical body and key after a timeout. For a
different, corrected request use a new key once rejection is confirmed.

Integrations that also want a Logi membership can explicitly send
`createMembership=true`, `gameId`, `type` and `status` (default `pending`).
Only a missing assignment for that game is created; existing memberships are
preserved. Pending applications can coexist with other memberships. Promotion
is not part of account registration or an implicit result of submitting a form.
For native Logi application decisions, use Logi's own workflow described below.

The existing `GET /api/v1/clan/users/{discordId}` remains limited to users already
assigned to the key's clan. A 404 does not prove that a global Logi account is
absent: the registration endpoint resolves that itself. No global user-directory
lookup is exposed through a clan API key.

## Native Logi applications

A clan application is one form in several Discord windows. The player fills
the windows one after another and sends the application only at the end, after
a review. Only then does the bot create a private application thread with the
answers, the welcome message and the decision buttons. Configure it in
**Settings → Membership** (the page is called **Clan application**).

## The settings page

The switch **Applications on** next to the title turns the whole flow on or
off. The page has four tabs: **Application**, **Categories** (with the number
of categories), **Attendance points** and **Role changes**. The save bar at the
bottom counts the unsaved changes; saving updates the panel in Discord by
itself. **Discard** drops every unsaved change.

### Panel and channels

- **Panel channel**: where the bot posts the panel with the **Apply** button.
  Under the select, Logi asks Discord whether the bot can post and embed
  images there.
- **Where application threads are created**: the text channel that holds the
  private threads. Logi checks that the bot can create private threads, send
  messages in them and manage them.
- **Title**, **Text** and an optional **Image** above the title. Upload a PNG,
  JPEG or WebP image of up to 2 MiB or choose one the clan already uploaded.
  The current image remains selected and visible in the preview when you save
  unrelated application settings; use **Remove image** only when you intend to
  clear it.
  The categories are listed under the text automatically. A new clan starts
  with "Join the `{clan}` clan" and "Choose how you want to play with us. The
  application has three short windows and takes a few minutes." in the clan
  language (two windows when no category has clan questions). A clan that
  never changed the title or text, including the older default, gets this
  text in the clan language too; text the clan wrote stays as it is.
- **Panel colour**: the bar of the panel card; empty uses the clan colour.
- The preview beside the fields shows the panel as Discord will show it, in
  the clan language.

### Form: windows and questions

An application selects one game and one category for that game. The category
sets the application’s Discord thread, invited recruiters, membership record
and decision scope; applicants cannot submit a combined multi-game application.

- **Window 1 · About you** always asks for the game (only when the clan plays
  more than one game), the category and the in-game name, then the clan's
  questions for this window. Everyone sees window 1, so its questions cannot be
  limited to a game or category.
- **Window 2 · Game accounts** asks for Steam and, for Hell Let Loose, Epic,
  Xbox and PlayStation. Accounts the player already has in Logi are prefilled.
  **Require verified Steam** (Hell Let Loose) sends the player to verify Steam
  on the Logi website before window 2; a typed Steam ID is then not accepted.
- **Window 3 · Clan questions** and the optional windows **3b** and **3c**
  hold the clan's own questions.

Question types are **Short text**, **Long text**, **Select**,
**Multi-select**, **Yes/no** and **Number**. Each question has a label of at
most 45 characters (the counter shows Discord's limit), an optional help line
of at most 100 characters and a placeholder. Selects have up to 25 options;
a multi-select also has **Pick from** and **to**. Outside window 1 a question
can be limited to one game and to some categories. Drag a question by its
handle, or focus the handle and use the arrow keys, to reorder it.

Discord allows at most five fields in one window. Each window shows how many
fields the applicant who sees the most questions gets; a full window says so
and offers **Add window**. Beside the windows, the page previews one window as
a Discord window and the review message the applicant sees before sending.

### Categories

The table lists what the applicant chooses from in window 1, each with a
two-letter badge (for example "HČ" for Hlavní člen, "ZA" for Záloha): the
game, the roles after acceptance (recruit → final), who sees the thread and
the switch **Ask for specialization**. The specialization question is asked only in Hell
Let Loose categories that have the switch on; it is disabled for Wardogs
categories. **Edit** opens the category on the **Categories** tab, where its
name and description (shown in the panel after the name and the game, and
under the name in the category select of window 1), roles and support roles
are edited. The clan role is selected in **Roles and access**. Each category's
**Roles by status** section independently chooses whether that role is granted
to recruits and to approved members; the latter switch also controls
mercenaries. Existing categories keep granting it until an administrator turns
one of those switches off.

### After sending

- The bot always creates a private thread with the answers and the welcome
  message. The welcome may use `{applicant}`, `{support_roles}` and
  `{category}`.
- **Mention the category's support roles in the thread** and **Add support
  role members individually** decide how support staff get into the thread.
- **Give the Recruit role right after sending** applies to categories that
  have a recruit role. The applicant then waits with the recruit role only;
  the clan role comes with acceptance, so a rejection takes away just the
  recruit role.
- **Send the applicant a confirmation DM** sends the thread link.
- An unfinished application is kept for 24 hours, then deleted.

The decision preview shows the card in the thread with its buttons:
**Accept as member**, **Accept as recruit**, **Accept as mercenary**,
**Reject…** (asks for a reason) and **Not decided yet** (leaves a note on the
card without a DM). The card shows **Waiting for a decision** until someone
decides, also when the applicant already has the recruit role. The table under
it shows the roles each button gives (+) and takes away (−) for the previewed
category, for example "− @Recruit" for **Reject…** when the recruit role is
given right after sending. Category support and Logi admins may decide; Logi
reloads the decider's roles from Discord when the button is pressed.
`/close_application` keeps working with the same check.

**Accept as mercenary** gives the roles of the clan's **mercenary category**
(a category whose result is Mercenary), not those of the category the
applicant chose: the applicant's own category when it is a mercenary one,
else the mercenary category of the same game, then of another game the
applicant chose, then any. The membership moves to that category and its
game. Without a mercenary category the button is disabled in Discord with a
short reason, `/close_application` with the mercenary outcome answers that the
category is missing, and the settings page says that a mercenary category has
to be set up first.

### Variant B · filling in on the web

**Also offer filling in on the web** is off by default. When it is on, the
panel gets a second button that opens the same form on a Logi page after
signing in with Discord. The application ends in the same thread with the
same card and roles. While the switch is off, the page does not exist.

## What the applicant sees

<Steps>

### Apply

The player presses **Apply** in the panel. A private message shows the steps;
**Continue** opens the next window, because Discord cannot open a window
directly from a window. Each window is saved when it is sent; a window with a
mistake keeps its correct answers, so **Edit** reopens it filled in. The bot
keeps the clan's form ready and updates it as soon as the settings are saved,
so a window opens at once, within Discord's three-second limit. In the
game-accounts window, **Have we seen you on the clan's servers?** offers the
players with the in-game name from window 1 found in the games stored from the
clan's servers, the same search `/link` uses; a date within the last week
shows the weekday ("Sat 3/10"), an older one only the date. Before the
game-accounts window, **Find my account ID** runs the same guide as `/link`
inside the application; once the account is linked, the private message
returns to the application and the window opens with the account filled in.
While an application is open, `/link` marks the accounts it uses when the
player wants to unlink one.

### Review

After the last window the private message shows every step with **Edit** and
one **Send application**. Nothing is visible to staff until then.

### Decision

The bot creates the private thread and posts the card. After the decision it
updates the card, changes the roles and sends the applicant a DM in the clan
language that names the roles without mentions and quotes a rejection reason.
The decision DM can be switched off in **Settings → Messages and panels**;
the decider's reply then says that no DM was sent. Role changes an admin
must fix (the bot's role is too low, a role was deleted) reach the errors
channel as one report listing the affected members.

</Steps>

## Website API

`GET/PATCH /api/v1/clan/settings` exposes the settings as the
`membershipApplication` slice: the switches, channels, panel texts, the whole
form and the per-category specialization switch. Decisions are Discord thread
actions and have no API operation; images are uploaded in the dashboard.

<Callout type="warning">
    The bot needs View Channel, Send Messages, Embed Links, Attach Files and
    Read Message History in the panel channel, and View Channel, Create Private
    Threads, Send Messages in Threads and Manage Threads in the thread channel.
    Anyone with Manage Threads can see private threads; give it only to staff.
</Callout>

## Test the complete path

1. Apply from an account without staff roles and check every window, the
   review and the thread's visibility.
2. Decide with a support role, then check that an unrelated member cannot use
   the buttons or `/close_application`.
3. Use a disposable recruit and final role first and confirm the role changes
   on **Role changes** before using production roles.
